# detailed-design (A-SPICE SWE.3 — 상세 설계)

## 입력
- 인자(`$ARGUMENTS`): 상세 설계할 컴포넌트 ID 또는 아키텍처 문서 경로 (기본 `docs/architecture/ARCH.md`)
- 리뷰 완료된 아키텍처 설계가 없으면 `architecture-design` 스킬을 먼저 수행하도록 안내한다.

## 핵심 규칙

1. 각 컴포넌트를 **모듈**로 분해해 정의한다. 모듈은 소스 파일(.c/.h 또는 .cpp/.h) 단위와 대응시킨다.
2. **인터페이스 정의 기준 수준**을 설계서 첫머리에 명시한다 (기본값: 다른 모듈이 호출하는 함수가 하나라도 있는 모듈).
   기준 이상의 모듈은 인터페이스를 **반드시** 정의한다.
3. **인터페이스가 정의된 모듈은 오직 인터페이스를 통해서만 통신한다.**
   공개 헤더에 선언된 함수 외에는 접근하지 않으며, 다른 모듈의 전역 변수·내부(static) 함수·구현 헤더에 의존하지 않는다.
4. **클린 코드 원칙**을 준수한다: 의도를 드러내는 이름, 작은 함수, 부작용 최소화, 중복 제거, 매직 넘버 제거, 주석은 "왜"만 설명.
5. **단일 책임 원칙**: 모듈과 함수는 각각 변경될 이유가 하나다.

## 절차

1. 컴포넌트의 인터페이스(ARCH-I)와 담당 요구사항을 확인한다.
2. 컴포넌트를 모듈로 분해하고 모듈별 책임을 정의한다.
3. 모듈의 공개 인터페이스(함수 시그니처, 타입, 오류 코드)를 정의한다. 아키텍처 인터페이스와 1:1로 대응하도록 한다.
4. 모듈의 내부 구조를 정의한다: 데이터 구조, 함수 목록, 함수별 동작(의사코드 또는 순서도·상태도).
5. 점검표로 설계를 점검하고 위반을 수정한다.
6. 추적성 매트릭스에 `ARCH ID → DD ID`를 기록한다.
7. `docs/detailed-design/<컴포넌트>.md`에 저장하고 `review` 스킬로 리뷰를 요청한다.

## 모듈 정의 형식 (`DD-M-xxx`)

| 속성 | 내용 |
|------|------|
| ID / 이름 / 파일 | `DD-M-001` / 이름 / 소스·헤더 경로 |
| 소속 컴포넌트 | ARCH-C ID |
| 책임 | 한 문장 |
| 인터페이스 | 공개 함수 목록 (정의 대상이면 `DD-I-xxx`), 없으면 "기준 미만" 표시 |
| 의존 모듈 | 호출하는 다른 모듈의 인터페이스만 기재 |
| 데이터 | 모듈 내부 데이터(비공개)와 그 불변 조건 |

## 함수 정의 형식 (`DD-F-xxx`)

| 속성 | 내용 |
|------|------|
| 시그니처 | 반환 타입, 이름, 파라미터(in/out, 단위, 유효 범위) |
| 반환값 | 정상/오류 값 정의. 의미 있는 반환값이 없으면 실행 결과 코드(예: `STATUS_OK`/`STATUS_ERR_*`)를 정의한다. |
| 동작 | 의사코드. **반환문은 함수 마지막에 한 번만** 있도록 구조화한다 (구현 스킬 규칙과 일치). |
| 오류 처리 | 입력 검증, 오류 시 상태 |
| 추적 | 구현하는 SRS ID, 상위 ARCH ID |

## 설계 점검표

- 인터페이스 기준 이상의 모든 모듈에 인터페이스가 정의되어 있다.
- 모듈 간 의존이 인터페이스(공개 헤더)로만 이루어져 있다.
- 모듈·함수 이름이 역할을 드러낸다 (`process`, `handle`, `do` 같은 모호한 동사 단독 사용 금지).
- 함수가 한 가지 일만 한다. 설명에 "그리고"가 필요하면 분리한다.
  소스 품질 기준(CLAUDE.md 2.3, Lizard 검사)에 맞게 **함수당 순환 복잡도 10 이하, 80라인 이하**가 되도록 설계한다 (예외 없음).
  권장: 인자 4개 이하, 가능한 한 짧은 함수.
- 모든 함수의 반환값이 정의되어 있고, 반환은 한 번이다.
- 모든 SRS(해당 범위)가 모듈·함수에 매핑되었고, 설계 요소는 모두 SRS로 거슬러 올라간다.
