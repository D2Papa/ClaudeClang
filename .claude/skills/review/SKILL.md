# review (A-SPICE 산출물 리뷰)

모든 산출물은 이 스킬로 리뷰한다. 다른 개발 스킬(`requirements-analysis`, `architecture-design`, `detailed-design`,
`implementation`, `unit-test`, `integration-test`)은 산출물을 만든 뒤 이 스킬로 리뷰를 요청한다.

## 입력
- 인자(`$ARGUMENTS`): 리뷰 대상 파일 또는 디렉터리 (예: `docs/requirements/SRS.md`, `src/sensor.c`)
- 산출물 종류를 인자나 경로로 판별한다. 판별이 모호하면 사용자에게 확인한다.

## 원칙

- 체크리스트 항목마다 **판정 근거(증거)** 를 남긴다. 근거 없이 "적합"으로 판정하지 않는다.
- 작성자가 결과를 설명해 주기를 기대하지 말고 산출물과 추적 대상 문서를 **직접 읽고** 확인한다.
- 리뷰어는 산출물을 수정하지 않는다. 결함을 기록하고 수정은 작성 스킬이 처리한다 (독립성).
  자동 수정을 요청받은 경우에만 수정하고, 수정 후 재리뷰한다.
- 추적성은 양방향으로 실제 대상 문서를 열어 확인한다 (ID가 존재하는지, 내용이 일치하는지).

## 절차

1. 산출물 종류를 정하고 `checklists.md`에서 해당 체크리스트를 읽는다. 체크리스트 위치:
   `.claude/skills/review/checklists.md`
2. 산출물과 상위/하위 추적 대상 문서를 읽는다.
3. 체크리스트 항목을 하나씩 판정한다: **적합(Pass) / 부적합(Fail) / 해당 없음(N/A, 사유 필수)**.
4. 부적합 항목은 결함으로 기록한다 (아래 형식).
5. 리뷰 보고서를 `docs/reviews/<산출물>-review-<YYYYMMDD>.md`로 저장한다.
6. 종합 판정을 낸다.
   - **승인**: 부적합 0건
   - **조건부 승인**: 경미한 결함만 있고 수정 계획이 있다 (재리뷰는 수정 항목만)
   - **반려**: 중대 결함이 있다 (수정 후 전체 재리뷰)
7. 체크리스트에 없는 새로운 결함 유형을 발견하면 `checklists.md` 갱신을 사용자에게 제안한다.

## 리뷰 보고서 형식

```markdown
# 리뷰 보고서: <산출물 이름>

- 대상: <파일 경로 / 버전(커밋)>
- 산출물 종류: <요구사항 | 아키텍처 | 상세 설계 | 소스 코드 | 단위 테스트 | 통합 테스트>
- 일자: <YYYY-MM-DD>
- 종합 판정: <승인 | 조건부 승인 | 반려>

## 체크리스트 결과
| ID | 항목 | 판정 | 근거 |
|----|------|------|------|

## 결함 목록
| 번호 | 심각도 | 위치 | 설명 | 수정 제안 |
|------|--------|------|------|-----------|

## 추적성 확인
- 상향 누락: ...
- 하향 누락: ...

## 요약
- Pass n / Fail n / N/A n
```

심각도: **중대**(요구 위반, 추적성 단절, 안전·보안 영향, 규칙 위반) / **경미**(표현, 형식, 일관성).

## 체크리스트 관리

- 체크리스트는 A-SPICE 기본 관행(SWE.1~SWE.6, SUP.2 검증의 작업 산출물 특성)과 이 프로젝트의 규칙
  (각 개발 스킬에 명시된 규칙)에서 도출했다.
- 체크리스트 항목은 안정 ID(예: `REQ-03`)를 가지며, 개정할 때는 항목 ID를 재사용하지 않는다.
- 프로젝트의 ASPICE 대상 수준·테일러링(해당 없음 허용 범위)이 따로 있으면 사용자에게 확인하고 반영한다.
