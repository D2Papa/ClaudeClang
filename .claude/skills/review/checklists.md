# 산출물별 리뷰 체크리스트

판정: Pass / Fail / N/A(사유 필수). 심각도 기본값은 항목 끝의 괄호: (중) 중대, (경) 경미.

## 1. 요구사항 (SWE.1)

| ID | 점검 항목 |
|----|-----------|
| REQ-01 | 모든 요구사항에 영구·고유 ID가 있다 (중) |
| REQ-02 | 기능 / 비기능(품질·제한·제약)으로 올바르게 분류되어 있다 (중) |
| REQ-03 | 기능 안전 요구사항이 이 문서에 없고 별도 안전 문서에서 관리된다. 필요한 경우 ID만 참조한다 (중) |
| REQ-04 | 품질 요구사항이 ISO 25010 품질 특성·하위 특성으로 분류되어 있다 (중) |
| REQ-05 | 한 요구사항에 한 가지 요구만 있다 (경) |
| REQ-06 | 모호한 표현("빠르게", "적절히" 등) 없이 수치·합격 기준으로 검증 가능하다 (중) |
| REQ-07 | 검증 방법(시험/분석/검사/시연)과 합격 기준이 있다 (중) |
| REQ-08 | 요구사항 간 충돌·중복이 없다 (중) |
| REQ-09 | 구현 방법이 아니라 "무엇"을 기술한다 (제약 요구사항 제외) (경) |
| REQ-10 | 상위 요구사항과의 상향 추적이 있고 내용이 일치한다 (중) |
| REQ-11 | 추적성 매트릭스에서 하향 추적(아키텍처·설계·코드·테스트)이 끊기지 않는다 (중) |
| REQ-12 | 근거·우선순위·상태 속성이 기록되어 있다 (경) |

## 2. 소프트웨어 아키텍처 설계 (SWE.2)

| ID | 점검 항목 |
|----|-----------|
| ARC-01 | 모든 컴포넌트가 정의되어 있고 책임이 한 문장으로 설명된다 (중) |
| ARC-02 | 모든 컴포넌트에 인터페이스가 정의되어 있다 (제공/요구) (중) |
| ARC-03 | 인터페이스 정의가 완전하다: 시그니처, 파라미터 방향·타입·범위, 반환값, 사전·사후 조건, 오류 처리 (중) |
| ARC-04 | 컴포넌트 간 통신이 인터페이스를 통해서만 이루어진다 (직접 접근 의존이 없다) (중) |
| ARC-05 | 순환 의존이 없다 (중) |
| ARC-06 | 응집도가 높다 (컴포넌트 책임이 단일 목적) (경) |
| ARC-07 | 결합도가 낮다 (공유 전역 데이터 없음, 인터페이스에 내부 구현 노출 없음) (중) |
| ARC-08 | 캡슐화·모듈화가 지켜진다 (경) |
| ARC-09 | SOLID 원칙(S·O·L·I·D)을 위반하지 않는다 (경) |
| ARC-10 | 정적 구조와 동적 구조(주요 시나리오)가 기술되어 있다 (경) |
| ARC-11 | 비기능 요구사항(품질·제한·제약)을 고려한 근거가 있다 (중) |
| ARC-12 | 모든 기능 SRS가 컴포넌트에 배정되었고(상향), 모든 컴포넌트가 SRS와 연결된다(하향) (중) |
| ARC-13 | 설계 대안·결정 근거가 필요한 곳에 기록되어 있다 (경) |

## 3. 소프트웨어 상세 설계 (SWE.3)

| ID | 점검 항목 |
|----|-----------|
| DDS-01 | 모든 컴포넌트가 모듈로 분해되어 있고 모듈 책임이 정의되어 있다 (중) |
| DDS-02 | 인터페이스 정의 기준 수준이 명시되어 있다 (중) |
| DDS-03 | 기준 이상의 모든 모듈에 인터페이스가 정의되어 있다 (중) |
| DDS-04 | 모듈 인터페이스가 아키텍처 인터페이스(ARCH-I)와 일치한다 (중) |
| DDS-05 | 모듈 간 의존이 공개 인터페이스로만 이루어진다 (중) |
| DDS-06 | 모든 함수에 반환값(정상/오류 값 정의)이 있고 `void` 반환이 없다 (중) |
| DDS-07 | 함수 동작 기술이 단일 반환 구조(반환 한 번)로 되어 있다 (중) |
| DDS-08 | 단일 책임 원칙: 모듈·함수가 변경될 이유가 하나다 (중) |
| DDS-09 | 이름이 의도를 드러낸다. 매직 넘버 대신 상수가 정의되어 있다 (경) |
| DDS-10 | 설계된 함수가 소스 품질 기준(순환 복잡도 10 이하, 80라인 이하)을 지킬 수 있는 크기·복잡도다. 예외는 허용하지 않는다 (중) |
| DDS-11 | 입력 검증·오류 처리·경계 조건이 기술되어 있다 (중) |
| DDS-12 | ARCH와 SRS로의 상향 추적, 소스·테스트로의 하향 추적이 있다 (중) |

## 4. 소스 코드 (SWE.3 구현)

| ID | 점검 항목 |
|----|-----------|
| SRC-01 | 모든 함수가 반환값을 가진다 (`void` 함수 없음; 예외는 설계서에 명시된 것만) (중) |
| SRC-02 | 모든 함수에서 `return`이 함수 마지막에 정확히 한 번만 있다 (조기 반환 없음) (중) |
| SRC-03 | 의미 있는 반환값이 없는 함수는 정상 실행 여부를 판단할 수 있는 상태 코드를 반환한다 (중) |
| SRC-04 | 구현이 상세 설계와 일치한다 (설계에 없는 동작·함수가 없다, 누락도 없다) (중) |
| SRC-05 | 모듈이 공개 인터페이스(헤더)로만 다른 모듈을 사용한다. 내부 함수·데이터는 `static`/비공개다 (중) |
| SRC-06 | 입력 검증과 오류 처리가 설계대로 구현되어 있다 (중) |
| SRC-07 | 클린 코드: 의도를 드러내는 이름, 작은 함수, 중복 없음, 매직 넘버 없음, 주석은 "왜"를 설명한다 (경) |
| SRC-08 | 모든 파일·함수에 Doxygen 주석(`@brief`, `@param`, `@return`, `@trace`)이 있다 (경) |
| SRC-13 | 모든 파일·함수 주석에 Human in the Loop 정보(`@par AI 작성 정보`: 모델·작성일·요청자, `@par 사용자 리뷰`: 완료 여부·리뷰일·리뷰어)가 있다 (중) |
| SRC-14 | 사용자 리뷰 "완료"는 사용자가 확인한 경우에만 표시되어 있고 리뷰일·리뷰어가 기재되어 있다. AI가 임의로 "완료"로 바꾼 흔적이 없다 (중) |
| SRC-15 | Cppcheck 경고 0건이고 `cppcheck-suppress` 등 예외 처리가 없다 (중) |
| SRC-16 | Lizard 기준(순환 복잡도 10 이하, 함수 80라인 이하)을 모든 함수가 만족한다 (중) |
| SRC-17 | TDD 테스트(`test/tdd/`)가 존재하고 단위 테스트와 분리되어 있으며, 별도 결과·커버리지가 있다 (중) |
| SRC-09 | 경고 없이 빌드된다 (`-Wall -Wextra -Werror`) (중) |
| SRC-10 | 데드 코드·미사용 변수·주석 처리된 코드가 없다 (경) |
| SRC-11 | 호출한 함수의 반환값을 확인하거나, 무시하는 이유가 주석으로 남아 있다 (중) |
| SRC-12 | 소스 → 상세 설계(DD ID) 추적이 있다 (중) |

## 5. 단위 테스트 (SWE.4)

| ID | 점검 항목 |
|----|-----------|
| UTS-01 | MC/DC 커버리지 100%, 테스트 성공률 100%를 달성했다 (중) |
| UTS-02 | 커버리지 측정 증거(LLVM 리포트)가 있고 TDD 테스트와 분리되어 측정되었다 (중) |
| UTS-03 | 모든 결정의 모든 조건이 독립성을 입증한다 (중) |
| UTS-04 | 모든 테스트 함수에 Doxygen 주석으로 목적·입력값·절차·예상 출력값이 있다 (중) |
| UTS-05 | 예상 출력값이 상세 설계·요구사항에서 도출되었다 (코드 실행 결과를 그대로 복사한 것이 아니다) (중) |
| UTS-06 | 모든 케이스에 의미 있는 assertion이 있고 커버리지만을 위한 케이스가 없다 (중) |
| UTS-07 | 경계값 분석, 동치 클래스, (파라미터 3개 이상일 때) PICT 조합이 적용되었고 기법이 기록되어 있다 (경) |
| UTS-08 | Stub/Mock이 필요한 곳에만 쓰였고 실제 모듈로 대체 가능한 곳에서 남용되지 않았다 (경) |
| UTS-09 | 무효 입력·오류 경로 테스트가 있다 (중) |
| UTS-10 | 커버리지 예외 처리(제외 주석·예외 목록)가 없다. 도달 불가 코드는 코드를 고쳐 해소했다 (중) |
| UTS-11 | 테스트 → 상세 설계/SRS 추적이 있고, 모든 함수·요구사항에 테스트가 있다 (중) |
| UTS-12 | 테스트가 독립적이다 (실행 순서·공유 상태에 의존하지 않는다) (경) |
| UTS-13 | 테스트 결과(통과/실패)가 기록되어 있고 실패는 원인과 조치가 있다 (중) |

## 6. 통합 테스트 (SWE.5)

| ID | 점검 항목 |
|----|-----------|
| ITS-01 | 통합 전략·순서와 근거가 테스트 계획에 있다 (경) |
| ITS-02 | 함수 커버리지 100%, 테스트 성공률 100%를 달성했다. 인터페이스 커버리지 표도 있다 (중) |
| ITS-03 | 아키텍처의 모든 인터페이스에 정상·경계·무효·오류 전파 케이스가 있거나 N/A 사유가 있다 (중) |
| ITS-04 | 인터페이스(컴포넌트 간 연동) 중심 테스트이고 컴포넌트 내부 로직 검증으로 채워지지 않았다 (중) |
| ITS-05 | 모든 테스트 함수에 Doxygen 주석으로 목적·입력값·절차·예상 출력값이 있다 (중) |
| ITS-06 | 예상 출력값이 아키텍처 인터페이스 정의·요구사항에서 도출되었다 (중) |
| ITS-07 | 커버리지만을 위한 의미 없는 케이스가 없다 (중) |
| ITS-08 | Stub/Mock은 미구현·외부 대상에만 쓰였고, 대상 컴포넌트는 실제 구현이 연결되었다 (중) |
| ITS-09 | 경계값 분석, 동치 클래스, PICT 조합이 적용되었고 기법이 기록되어 있다 (경) |
| ITS-10 | 호출 순서·시나리오(동적 구조) 테스트가 있다 (경) |
| ITS-11 | 테스트 → 아키텍처(ARCH-I)/SRS 추적이 있다 (중) |
| ITS-12 | 결과가 기록되어 있고, 실패는 원인(구현/인터페이스 정의)과 조치가 있다 (중) |
