# architecture-design (A-SPICE SWE.2)

## 입력
- 인자(`$ARGUMENTS`): 설계 대상 범위 또는 SRS 경로 (기본 `docs/requirements/SRS.md`)
- 승인(또는 리뷰 완료)된 SRS가 없으면 `requirements-analysis` 스킬을 먼저 수행하도록 안내한다.

## 핵심 규칙

1. **컴포넌트를 정의한다.** 각 컴포넌트는 책임 한 문장으로 설명되고, 담당 SRS 요구사항이 있어야 한다.
2. **모든 컴포넌트는 인터페이스를 반드시 정의한다.** 인터페이스 없는 컴포넌트는 허용하지 않는다.
3. **컴포넌트 간 통신은 오직 인터페이스를 통해서만 한다.** 다른 컴포넌트의 내부 데이터·함수·헤더에 직접 접근하는 의존성은 설계에 넣지 않는다.
4. **응집도는 높이고 결합도는 낮춘다.**
5. **모듈화, 캡슐화, SOLID 원칙을 준수한다.**

## 절차

1. SRS를 읽고 기능 요구사항을 책임 단위로 묶어 컴포넌트 후보를 만든다.
2. 비기능 요구사항(품질·제한·제약)이 구조에 미치는 영향을 정리한다 (예: 성능 제한 → 계층 수 제한).
3. 컴포넌트와 인터페이스를 정의한다.
4. 컴포넌트 간 의존 관계도(정적 구조)와, 핵심 시나리오의 동작 흐름(동적 구조)을 그린다. 다이어그램은 Mermaid로 작성한다.
5. 아래 점검표로 설계를 점검하고 위반을 수정한다.
6. 추적성 매트릭스에 `SRS ID → ARCH ID`를 기록한다.
7. `docs/architecture/ARCH.md`에 저장하고 `review` 스킬로 리뷰를 요청한다.

## 컴포넌트 정의 형식 (`ARCH-C-xxx`)

| 속성 | 내용 |
|------|------|
| ID / 이름 | `ARCH-C-001` / 이름 |
| 책임 | 한 문장. "그리고"가 들어가면 분리를 검토한다. |
| 제공 인터페이스 | 이 컴포넌트가 외부에 제공하는 인터페이스 ID 목록 |
| 요구 인터페이스 | 이 컴포넌트가 다른 컴포넌트로부터 필요로 하는 인터페이스 ID 목록 |
| 담당 요구사항 | SRS ID 목록 |
| 비기능 고려 | 해당하는 SRS-Q/L/C 항목과 대응 방안 |

## 인터페이스 정의 형식 (`ARCH-I-xxx`)

| 속성 | 내용 |
|------|------|
| ID / 이름 | `ARCH-I-001` / 이름 |
| 제공자 → 사용자 | 컴포넌트 ID 관계 |
| 동작(함수 시그니처) | 이름, 파라미터(방향 in/out, 타입, 단위, 범위), 반환값(성공/오류 코드 정의) |
| 사전·사후 조건 | 호출 전 만족해야 할 조건, 호출 후 보장되는 상태 |
| 오류 처리 | 오류 코드와 호출자의 기대 동작 |
| 타이밍·자원 | 호출 주기, 최대 소요 시간, 동기/비동기, 스레드 안전성 (해당 시) |

## 설계 점검표

- 응집도: 컴포넌트 내부 요소가 같은 목적을 위해 모여 있다. 기능이 흩어지거나 "잡동사니(utils)" 컴포넌트가 없다.
- 결합도: 순환 의존이 없다. 의존 방향이 안정적인 쪽(추상)을 향한다. 공유 전역 데이터가 없다.
- 캡슐화: 내부 데이터는 비공개이고 인터페이스로만 접근된다. 인터페이스에 내부 구현 타입이 노출되지 않는다.
- SOLID
  - S: 컴포넌트가 변경될 이유가 하나다.
  - O: 기능 추가가 기존 컴포넌트 수정 없이 확장으로 가능하다.
  - L: 같은 인터페이스를 구현한 컴포넌트는 서로 대체 가능하다.
  - I: 인터페이스가 사용자별로 작고 구체적이다 (사용하지 않는 동작을 강요하지 않는다).
  - D: 상위 컴포넌트가 하위 구현이 아니라 인터페이스에 의존한다.
- 추적성: 모든 컴포넌트가 SRS와 연결되고, 모든 기능 SRS가 컴포넌트에 배정되었다.
