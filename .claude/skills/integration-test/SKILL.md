# integration-test (A-SPICE SWE.5 — 통합 및 통합 테스트)

## 입력
- 인자(`$ARGUMENTS`): 통합 대상 컴포넌트 ID(들)과 커버리지 목표
- 대상 컴포넌트의 단위 테스트가 통과한 상태여야 한다. 아니면 `unit-test` 스킬을 먼저 수행하도록 안내한다.
- 통합 테스트의 품질 기준(CLAUDE.md 2.1)은 **함수 커버리지 100%**, **테스트 성공률 100%** 이다. 예외 없이 달성해야 한다.
- 이와 별개로 설계 검증을 위해 **인터페이스 커버리지**(아키텍처에 정의된 모든 인터페이스 동작과 오류 경로를 한 번 이상 실행)도
  확인한다. 인터페이스 커버리지는 보조 지표이며 함수 커버리지를 대체하지 못한다.

## 핵심 규칙

1. **정해진 커버리지를 100% 달성할 때까지 테스트 케이스를 반복해서 추가한다.** (측정 → 미달 분석 → 추가 → 재측정)
2. **의미 없는 테스트로 수치를 채우지 않는다.** 아키텍처에 정의된 인터페이스 계약을 검증하는 케이스만 추가한다.
3. **Stub/Mock은 필요한 경우에만** 쓰고 의존하지 않는다. 통합 테스트의 목적은 실제 컴포넌트끼리 연동하는 것이므로,
   테스트 대상 컴포넌트들은 실제 구현을 연결한다. Stub/Mock은 아직 구현되지 않았거나 하드웨어·외부 시스템인 상대에만 쓴다.
4. **인터페이스 중심으로 테스트한다.** 컴포넌트 내부 로직 검증은 단위 테스트의 몫이다.
   통합 테스트는 인터페이스를 통한 호출·데이터 전달·오류 전파·타이밍·상태 연동을 검증한다.
5. **모든 테스트 함수에 Doxygen 주석**으로 테스트 목적, 입력값, 절차, 예상 출력값을 쓴다.

## 테스트 함수 주석 형식

```c
/**
 * @brief   [목적] Sensor가 범위 밖 값을 전달했을 때 Controller가 오류를 전파하는지 확인한다.
 * @par 입력값
 *   - Sensor_Read()가 반환하는 값 = 4096 (범위 밖)
 * @par 절차
 *   -# Sensor, Controller를 실제 구현으로 초기화한다.
 *   -# Controller_Step()을 호출한다.
 * @par 예상 출력값
 *   - Controller_Step() 반환값 == STATUS_ERR_INPUT
 *   - 액추에이터 출력은 안전 기본값 유지
 * @trace IT-004 -> ARCH-I-003, SRS-F-011
 * @technique 동치 클래스 (무효 클래스)
 */
```

## 테스트 설계 기법

단위 테스트와 같은 기법을 인터페이스 수준에서 적용한다.

| 기법 | 인터페이스 수준 적용 |
|------|----------------------|
| 동치 클래스 분할 | 인터페이스 파라미터와 상태의 유효/무효 클래스 |
| 경계값 분석 | 파라미터 범위 경계, 버퍼 크기, 호출 횟수·주기 경계 |
| PICT 조합 | 여러 인터페이스 파라미터·컴포넌트 상태·호출 순서의 조합 (`unit-test` 스킬의 PICT 사용법 참조) |
| 시퀀스 테스트 | 아키텍처의 동적 구조(시나리오) 순서대로 호출 / 잘못된 순서로 호출 |
| 오류 전파 | 하위 컴포넌트 오류가 상위로 전달되는 경로 |

## 절차

1. 아키텍처 설계서(`docs/architecture/ARCH.md`)에서 통합 대상의 컴포넌트, 인터페이스(ARCH-I), 동적 시나리오를 읽는다.
2. 통합 순서를 정한다 (하위 → 상위, 또는 시나리오 단위). 전략과 근거를 테스트 계획에 적는다.
3. 인터페이스별로 케이스를 설계한다: 정상 호출, 경계값, 무효 입력, 오류 전파, 호출 순서, 사전·사후 조건 위반.
4. 테스트 코드를 작성한다 (Doxygen 주석 포함).
5. 커버리지를 측정한다. 함수 커버리지는 `scripts/ci/coverage.sh`(스위트별 LLVM 측정, `claudeclangbuild` 컨테이너)로 확인하고,
   인터페이스 커버리지는 아키텍처 인터페이스 × 케이스 표로 확인한다. 통합 테스트는 `test/integration/`에 둔다.
6. 미달 항목마다 의미 있는 케이스를 추가하고 5번으로 돌아간다. 함수가 도달 불가능하면 예외로 처리하지 말고 코드·설계 결함으로 보고해 고친다.
7. 실패 원인이 인터페이스 정의 불일치(아키텍처 결함)인지, 구현 결함인지 구분해 보고한다.
8. 추적성 매트릭스에 `ARCH ID/SRS ID → IT ID`를 기록하고 `review` 스킬로 리뷰한다.

## 인터페이스 커버리지 표

```
| 인터페이스 | 정상 | 경계 | 무효 입력 | 오류 전파 | 순서 위반 | 케이스 ID |
|------------|------|------|-----------|-----------|-----------|-----------|
```
각 칸이 "해당 없음(사유)" 또는 케이스 ID로 채워져야 완료다.
